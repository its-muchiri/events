## What "MVP complete" means for this project
Per build-sequencing-roadmap.md, event.co.ke is third in the build order. Its MVP is: single-vendor booking (book one photographer/caterer/etc. independently), M-Pesa payment, and a basic e-commerce store (event supplies/decor) — built on shared modules 1–4 plus module 6 (Review & Dispute Console v1). **Multi-vendor bundles and date-locking are explicitly V2, and the roadmap says this must not be scheduled before rider.co.ke has launched** (module 8, Booking/Availability Engine v2, depends on module 3 being stable in production). This project's code already has BundleController.php and bundle-new.php/bundle-status.php views — that's fine to keep, but do not treat bundle features as required for DONE, and flag it as an open question if bundle work is progressing ahead of rider.co.ke's booking-engine v2 readiness.

- Customer can sign up / log in
- Customer can browse/search vendors by category (venue, catering, photography, decor, entertainment, etc.) and compare pricing/ratings/portfolio
- Customer can book a single vendor for their event date and pay a deposit via M-Pesa
- Customer can submit a review after the event
- Customer can buy event supplies/decor from the store
- Vendor can accept/decline a booking request and update its status
- Admin/coordinator can view bookings and triage disputes (vendor no-show/cancellation)
- Every image slot (homepage hero, vendor directory/profile portfolio photos, store product photos for decor/supplies) shows a real, topically relevant photo sourced from Unsplash — not a placeholder box or broken image
- App builds and runs with zero errors, works on mobile width
- Core flow (browse vendors → book one → pay deposit → track → review) covered by a smoke test

## Known issues / open questions
- Directory assumptions (this pass): (a) only suspended/banned vendors are hidden — vendors still `pending_verification` stay listed without the "Verified" badge, because there is no admin KYC-approval flow yet and hiding them would make every newly onboarded vendor invisible (an admin approve/reject action is still needed for the Admin checklist item); (b) a date counts as unavailable if the vendor's `vendor_availability` row is `is_booked` or they hold a `confirmed`/`at_risk`/`fulfilled` booking that day — dates with no row are open by default; (c) directory ratings are computed live from `reviews` (falling back to the denormalized `vendor_standing.average_rating`), so they update as soon as ReviewController writes a review; `vendor_standing` itself is still not refreshed by ReviewController — fix in the Review item.
- Vendors have no way to upload portfolio photos: onboarding accepts `portfolio_urls` as URLs only, and there is no vendor-onboard page. Until then vendors without a portfolio show per-category sample photos, labelled "Sample … photos — this vendor hasn't uploaded their own portfolio yet" on their profile (a documented, deliberate fallback, not a placeholder box). Non-http(s) portfolio URLs are dropped before rendering.
- `database/seed_demo.php` seeds 12 demo vendors (with completed bookings + reviews) for dev/demo only — never run in production; the "Remove stubs, TODOs, placeholder data" item should confirm nothing seeds automatically. Demo password is printed by the script.
- BookingController::create does not check vendor availability or that the vendor exists (a customer can book a date the vendor has already confirmed). `VendorDirectory::availabilityOn()` is ready to reuse — belongs to the "Error handling for the core single-vendor flow" item.
- Local dev: serve with `php -S 127.0.0.1:8000 -t public` (no router-script argument) so `/assets/*` is served statically; passing `public/index.php` as a router script makes the built-in server 404 the CSS/JS (on Vercel, vercel.json routes assets).
- Multi-vendor bundling (BundleController.php) is built ahead of its stated shared-module dependency (Booking/Availability Engine v2, gated on rider.co.ke's booking engine v1 being stable in production per build-sequencing-roadmap.md). Verify rider.co.ke's status before extending bundle features further; note here rather than stopping to ask.
- The rental-equipment-as-store-vs-booking question (tents/chairs/sound systems) is explicitly unresolved in prd.md — pick a reasonable default (booking-engine mechanism, per prd.md's own reasoning), log it here, and continue.
- There is no vendor-onboarding *page* (only the JSON POST /api/v1/vendors/onboard endpoint) — AuthController redirects a new vendor signup to /vendors rather than a dedicated onboarding form, since that view doesn't exist yet. A later pass should build src/Views/vendor-onboard.php + a PageController route so vendors can submit KYC docs/listing details through the browser, not just the API.
- Real M-Pesa Daraja STK Push is now wired (src/Core/Mpesa.php + PaymentController::stkPush), but B2C payout disbursement (actually moving KES to a vendor's M-Pesa account once Escrow::release() records the pending payout) is not built — a payout-batch job against Daraja's B2C API is future work, same gap laundry.co.ke has.
- No refund/deposit-forfeiture handling exists yet for BookingController::cancel — cancelling a paid booking doesn't touch its `payments`/`escrow_transactions` rows. open-questions.md #6 (deposit-forfeiture split between platform and vendor) is unresolved upstream, so this wasn't built rather than guessing the split. Flagging for a later pass.
- Local dev smoke-tested this pass (and the prior identity/auth pass) against a MySQL instance already listening on 127.0.0.1:3306 (matches .env) with the schema.sql tables present — signup, login, session cookie, /api/v1/auth/me, authenticated vs. unauthenticated booking creation, logout, M-Pesa stkPush validation paths (401/403/503), a simulated Daraja callback (including idempotent duplicate delivery), escrow hold + booking auto-confirm, booking-status auth guard (401/403), vendor-completes-booking escrow release, and vendor earnings — all verified working end-to-end via curl.
